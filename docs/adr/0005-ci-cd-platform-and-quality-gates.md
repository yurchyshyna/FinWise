# ADR-0005: Платформа CI/CD, версіонування артефактів і політика Quality Gates

**Статус:** прийнято
**Дата:** 2026-11-23

## Контекст

Проєкт FinWise складається з backend, воркера і frontend, які збираються в Docker-образи. Перевіряти код вручну перед кожним злиттям довго й ненадійно, тому потрібен автоматичний конвеєр, який перевіряє код, збирає образи й публікує їх у реєстр. Також потрібні правила, що саме вважається коректною зміною, і зрозуміла схема назв образів.

## Рішення

**Платформа CI/CD: GitHub Actions.** Репозиторій уже розміщено на GitHub, тому окремий сервер для CI не потрібен. Конвеєр описано в файлі `.github/workflows/ci.yml`. Для публікації образів використано GitHub Container Registry (GHCR), який працює з тим самим акаунтом.

**Стратегія гілок: GitHub Flow.** Є одна стабільна гілка `main` і короткі гілки для змін. Усі зміни потрапляють у `main` лише через Pull Request. Для `main` налаштовано захист: прямий пуш заборонено, потрібні успішні перевірки CI (Backend, Frontend, Dockerfiles, Image api, Image web) і одне схвалення. Для власника репозиторію залишено можливість обходу правил, бо в навчальному проєкті один учасник.

**Політика Quality Gates.** Pull Request не можна злити, поки не пройдуть усі перевірки:
- flake8 для Python-коду і ESLint для frontend;
- hadolint для Dockerfile;
- модульні тести pytest (база даних у них замінена заглушками, тому вони не потребують окремого сервера);
- сканування зібраних образів Trivy: уразливості рівня HIGH і CRITICAL, для яких уже є виправлення, зупиняють конвеєр. Уразливості без виправлення ігноруються, бо усунути їх не можна.
Образи збираються лише після успішних перевірок коду, а публікуються лише після успішного сканування.

**Версіонування артефактів.** Кожен образ отримує тег із коротким хешем коміту (`sha-c724ac3`), за яким завжди видно, з якого коду він зібраний. Для релізів використовується семантична версія: git-тег `v0.1.0` дає образу тег `0.1.0`. Тег `latest` ставиться лише для `main` і лише разом із тегом за хешем, самостійно його не використовуємо.

**Принцип «збираємо один раз».** У межах одного завдання образ збирається, скануються саме він, і саме цей образ відправляється в реєстр. У Pull Request образи тільки збираються й скануються, публікація відбувається лише з `main` і з тегів версій.

**Секрети.** Для входу в реєстр використовується вбудований токен `GITHUB_TOKEN`, який GitHub створює на кожен запуск. У репозиторії паролі не зберігаються. Завданню, яке публікує образи, видано лише право запису пакетів.

## Розглянуті альтернативи

- **GitLab CI/CD:** потребував би перенесення репозиторію.
- **Jenkins:** вимагає окремого сервера, який треба підтримувати.
- **GitFlow:** довгі гілки `develop` і `release` створюють зайву бюрократію для невеликого вебсервісу.
- **Docker Hub:** має обмеження на кількість завантажень, GHCR зручніший завдяки інтеграції з репозиторієм.

## Наслідки

**Плюси:**
- помилки стилю, тестів і відомі вразливості виявляються до злиття;
- кожен образ можна простежити до коміту, а також відкотитися на попередню версію;
- публікація не потребує ручних дій.

**Мінуси та обмеження:**
- у Dockerfile використано `apt-get upgrade` і `apk upgrade`, щоб отримати виправлення системних пакетів раніше, ніж оновиться базовий образ (для hadolint додано виняток DL3005). Через це збірки в різні дні можуть відрізнятися;
- перевірка Trivy залежить від актуальності його бази вразливостей, тому той самий код у різні дні може пройти або не пройти;
- модульні тести не перевіряють роботу з реальною базою даних, інтеграційних тестів поки немає;
- покриття коду тестами не вимірюється;
- версії сторонніх дій (actions) зафіксовано за тегами. Версію `trivy-action` вибрано не нижче `v0.36.0`, бо старіші теги було скомпрометовано в березні 2026 року;
- обхід правил захисту `main` для власника означає, що вимога схвалення на практиці не діє, поки в проєкті один учасник.
