# ADR-0006: Вибір платформи, зберігання стану Terraform і розподіл відповідальності між Terraform та Ansible
 
**Статус:** прийнято
**Дата:** 2026-11-24
 
## Контекст
 
Для запуску FinWise поза локальним комп'ютером потрібен сервер. Створювати його вручну в консолі провайдера і налаштовувати вручну по SSH ненадійно: такі дії важко повторити, у них легко помилитися, а в репозиторії не залишається опису того, як саме влаштована інфраструктура. Тому і створення сервера, і його налаштування описано кодом, який зберігається в репозиторії разом із рештою проєкту. Для цього використано Terraform (створення інфраструктури) і Ansible (налаштування сервера).
 
Потрібно було вирішити три питання: на якій платформі розгортати сервер (публічна хмара в межах безкоштовного ліміту чи локальний гіпервізор), де зберігати стан Terraform і як розділити відповідальність між Terraform та Ansible.
 
## Рішення
 
**Цільова платформа: AWS (безкоштовний план), регіон eu-north-1 (Стокгольм).** Основні причини вибору:
 
- сервер у публічній хмарі має реальну публічну IP-адресу і доступний з інтернету, тож у ньому можна перевірити і SSH, і майбутню роботу вебсервісу;
- AWS надає ті самі мережеві об'єкти, що використовуються в реальних проєктах (VPC, підмережі, таблиці маршрутів, Security Group), тому в коді видно, як будується захищена мережа, а не лише віртуальна машина;
- провайдер AWS для Terraform є одним із найпоширеніших, має докладну документацію і багато прикладів;
- безкоштовний план AWS покриває навчальне навантаження за рахунок кредитів, без власного обладнання.
Регіон визначено самим акаунтом: у безкоштовному плані доступний лише Стокгольм, інші регіони (зокрема Франкфурт) недоступні, тому використано його. Доступ до AWS для Terraform виконується через окремого IAM-користувача, а не через кореневий акаунт. Ключі доступу зберігаються лише локально в налаштуваннях AWS CLI і в репозиторій не потрапляють.
 
**Terraform відповідає за створення інфраструктури (провізіонінг).** У каталозі `infra/terraform` описано VPC, публічну підмережу, інтернет-шлюз, таблицю маршрутів, Security Group, пару SSH-ключів і віртуальну машину (Ubuntu 24.04, `t3.small`, диск gp3 на 20 ГБ). Усі значення, які можуть змінюватися, винесено у змінні, а IP-адреса і DNS-ім'я сервера повертаються як вихідні значення (outputs).
 
Security Group пропускає лише потрібний трафік: SSH (порт 22) тільки з однієї адреси адміністратора, HTTP (80) і HTTPS (443) звідусіль. Решта вхідного трафіку заборонена, зокрема порти бази даних та внутрішніх сервісів ззовні не відкриті. Для сервера вимагається IMDSv2 (захищений доступ до метаданих), а для всіх ресурсів додано теги `Project` і `ManagedBy`.
 
**Ansible відповідає за налаштування сервера (управління конфігурацією).** У каталозі `infra/ansible` описано inventory (адреса сервера береться з виводу Terraform) і playbook, який оновлює пакети, вмикає фаєрвол ufw і fail2ban, встановлює Docker Engine та плагін Compose з офіційного репозиторію Docker, додає користувача в групу `docker` і створює каталоги застосунку. Playbook ідемпотентний: другий запуск не змінює нічого (`changed=0`).
 
**Розподіл відповідальності.** Terraform створює і видаляє ресурси в хмарі, але не знає, що всередині сервера. Ansible налаштовує те, що всередині сервера, але не створює самі сервери. Така межа дозволяє змінювати кожну частину окремо: наприклад, переналаштувати сервер без його перестворення.
 
**Зберігання стану Terraform.** Стан (`terraform.tfstate`) зберігається локально і не потрапляє в Git, бо може містити чутливі дані. У `.gitignore` додано `*.tfstate`, каталог `.terraform/` і файл `terraform.tfvars` з реальними значеннями (в репозиторії лежить лише `terraform.tfvars.example`). Файл `.terraform.lock.hcl`, навпаки, зберігається в репозиторії, щоб усі використовували ті самі версії провайдера. Версію провайдера обмежено (`~> 6.0`). Локальне зберігання обрано, бо проєкт розробляє одна людина, а віддалене сховище вимагало б додаткових ресурсів (бакет S3, таблиця або механізм блокування) і прав, які теж треба було б спочатку створити.
 
## Розглянуті альтернативи
 
**Платформа:**
 
- **Google Cloud і Azure:** також мають безкоштовні або пробні періоди та працюють з Terraform. Вони були б прийнятним вибором, але AWS обрано через найбільшу поширеність і кількість матеріалів, а також тому, що його модель мережі (VPC, Security Group) добре підходить для показу принципу найменших привілеїв.
- **DigitalOcean:** простіший у використанні, але має менше мережевих можливостей, а безкоштовного плану в ньому немає, лише пробні кредити на обмежений строк.
- **Локальні гіпервізори (VirtualBox, Proxmox, Libvirt/KVM):** не потребують оплати і не залежать від хмари. Проте віртуальна машина на домашньому комп'ютері не має публічної адреси, її доступність залежить від самого комп'ютера, а Terraform-провайдери для таких середовищ менш зрілі. Крім того, на них неможливо показати хмарну мережу з VPC та Security Group.
**Зберігання стану Terraform:**
 
- **Віддалене сховище (S3 з блокуванням):** правильний варіант для команди, бо стан спільний, захищений блокуванням і має резервні копії. Для одного розробника це зайве ускладнення, тому не використано. Перехід на нього можливий пізніше без зміни самих ресурсів.
- **Зберігання стану в Git:** стан може містити чутливі дані (наприклад, ідентифікатори й атрибути ресурсів), а в історії репозиторію їх неможливо повністю прибрати, тому такий варіант відхилено.
## Наслідки
 
**Плюси:**
 
- інфраструктуру можна повністю видалити (`terraform destroy`) і створити заново тими самими командами;
- зміни інфраструктури видно в Pull Request, а `terraform plan` показує їх до застосування;
- сервер налаштовується однаково щоразу, а повторний запуск Ansible безпечний;
- паролі, ключі й стан не потрапляють у репозиторій.
**Мінуси та обмеження:**
 
- локальний стан Terraform означає, що його втрата призведе до розсинхронізації з реальними ресурсами, а одночасна робота кількох людей не захищена блокуванням. Для команди потрібне віддалене сховище стану;
- політика безкоштовного плану забороняє запити `DescribeImages`, тому ідентифікатор образу Ubuntu (AMI) задано вручну змінною `ami_id`, а не знаходиться автоматично. Його потрібно оновлювати самостійно, і він різний для кожного регіону;
- SSH відкрито лише для однієї IP-адреси. Якщо адреса змінюється, доступ до сервера втрачається, доки правило не оновлено;
- адресу сервера треба вручну переносити з виводу Terraform в inventory Ansible, а після перестворення сервера вона змінюється;
- фаєрвол ufw на сервері дублює правила Security Group. Це свідомо: так захист діє на двох рівнях, але правила треба змінювати в обох місцях;
- це один сервер без резервування: його вихід з ладу означає зупинку сервісу;
- Ansible не працює на Windows напряму, тому запускається з WSL, де для SSH-ключа потрібні правильні права доступу;
- сервер працює за рахунок кредитів, тому після демонстрації його потрібно видалити, щоб не витрачати їх.
